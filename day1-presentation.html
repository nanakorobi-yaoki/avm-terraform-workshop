2. Infrastructure as Code 入門

なぜ IaC が必要なのか

従来のインフラ管理では、Azure Portal でのクリック操作や手順書に基づく手動設定が一般的でした。この方法には以下のような課題があります:

  • 属人化 — 担当者しか手順を把握しておらず、引き継ぎが難しい
  • 環境ごとの差異 — dev / stg / prod で設定が少しずつ異なってしまう
  • 変更履歴の不透明さ — いつ・誰が・何を変えたのか追えない
  • 展開に時間がかかる — 同じ構成を複数環境に展開するのに手間がかかる
  • 構成のドリフト — コードと実環境の状態が乖離しても気づけない

IaC のメリット

メリット説明
再現性同じコードから同じ環境を何度でも作成
一貫性dev/stg/prod を同一テンプレートで管理
バージョン管理Git で変更履歴を追跡、PR でレビュー
自動化CI/CD パイプラインで自動デプロイ
監査対応Git のコミット履歴で「誰が・いつ・何を変更したか」を追跡できる
ドリフト検知terraform plan で、実環境とコードの差分をすぐに確認できる

3. Azure Verified Modules (AVM) とは

3.1 AVM が目指すもの

Azure Verified Modules (AVM) は、IaC モジュールの構築・利用・提供方法を標準化し、一貫性のあるベストプラクティスを提供するための Microsoft の取り組みです。Bicep と Terraform の両方に対応し、それぞれの言語固有のレジストリ（Terraform Registry / Bicep Registry）で公開されます。

AVM の目的は、質の高い IaC モジュールの定義・構築方法・利用方法を標準化することで、信頼性の高いモジュールを提供し、プロジェクトのスピードを加速させることです。

AVM ミッションステートメント: 「Well-Architected Framework の原則に従い、複数の IaC 言語で包括的な Azure Verified Modules ライブラリを提供すること。Microsoft が信頼できる唯一の情報源としてサポートし、Azure リソースとアーキテクチャパターンのデプロイ時間を短縮することで、すべての人と組織の IaC ジャーニーを支援する。」

3.1.1 なぜ AVM が必要なのか — 「One Microsoft」への統合

Microsoft 内部では、これまで多くの部門がそれぞれ独自に IaC モジュールを開発・提供してきました。しかし、各プロジェクトはコーディング規約、テストフレームワーク、サポート方針がバラバラで、ユーザーにとって「どれを信頼すべきか」が不明確でした。

  • 一貫性の欠如 — プロジェクトごとにスタイル・消費方法・テストが異なる
  • サポートの不透明さ — 個人開発のモジュールには公式サポートがなく、大規模エンタープライズでの採用障壁に
  • 重複する取り組み — 同じリソースに対して複数のモジュールが存在し、どれが最新か不明

AVM はこれらの課題を解決するため、「One Microsoft」として統一された戦略・定義・サポートのもとで IaC モジュールを提供します。

3.2 AVM はどのように信頼性を確保しているか

仕組み内容
1. Microsoft 公式サポートモジュール所有者が対応 → 3営業日以内に応答なければ AVM コアチームが介入 → セキュリティ問題は5営業日で製品グループにエスカレーション
2. 継続的メンテナンス各モジュールに所有者（Microsoft フルタイムエンジニア）を必須配置。GitHub Issue が放置されない体制
3. 明確な仕様への準拠言語共通の仕様 + Terraform 固有の仕様に沿って開発。モジュール間の一貫性と予測可能な動作を保証
4. WAF との整合性Well-Architected Framework の推奨事項（セキュリティ・信頼性・パフォーマンス・コスト最適化）に沿った既定値
5. ドキュメントと使用例各モジュールに詳細なドキュメントと具体的な使用例を提供。自己学習しやすい
6. 徹底的なテストリリース前に自動テストで仕様準拠と動作を検証

3.3 モジュールの分類

分類命名規則説明対象ユーザー
リソースモジュールavm-res-*単一のリソースを WAF ベストプラクティスの設定でデプロイ。RBAC、ロック、PE、診断設定などの共通インターフェースを統合。外部依存リソースは作成しない。個別リソースごとにベストプラクティスを適用したいユーザー
パターンモジュールavm-ptn-*複数のリソース（多くはリソースモジュールを内部利用）をまとめてデプロイ。Azure Architecture Center のパターン実装に最適。アーキテクチャパターンを簡単にデプロイしたいユーザー
ユーティリティモジュールavm-utl-*リソースやパターンモジュールで再利用可能な関数やルーチンを提供。Azure リソースは直接デプロイしない（デプロイスクリプト除く）。※ プレビュー段階共通関数やヘルパーをモジュール間で再利用したいユーザー

リソースモジュール例

avm-res-compute-virtualmachine、avm-res-keyvault-vault、avm-res-databricks-workspace

パターンモジュール例

Azure Landing Zone / Virtual WAN / Virtual Network Gateway / Hub Networking

ポイント: どのモジュールもパラメータを変更するだけで様々な構成にデプロイ可能。内部の複雑さを意識せず、ドキュメントを見ながら活用できます。

3.4 一貫インターフェース

すべての AVM モジュールが共通で提供するインターフェースです。どのリソースでも同じ書き方で設定できるため、学習コストが最小化されます:

  • tags — 共通タグ
  • lock — リソースロック（CanNotDelete / ReadOnly）
  • role_assignments — RBAC ロール割り当て
  • diagnostic_settings — 診断設定（Log Analytics / Event Hub）
  • managed_identities — マネージド ID（SystemAssigned / UserAssigned）
  • private_endpoints — プライベートエンドポイント
  • customer_managed_key — CMK 暗号化

3.5 Terraform ユーザにとっての変化とメリット

以前は Terraform Verified Modules (TFVM) が提供されていましたが、AVM の登場により、AVM 仕様に沿って開発された信頼性の高いモジュールを利用して Azure リソースをプロビジョニングできるようになりました。一部の TFVM モジュールは AVM への切り替えを促しています。

3.6 モジュール開発者にとってのメリット

AVM はモジュールを利用するだけでなく、開発する側にもメリットがあります。AVM の仕様やテスト手法は、Microsoft が「One Microsoft」として公開している Terraform のベストプラクティスです。この知見を自組織のモジュール開発に取り入れることで、社内モジュールの信頼性を高めることができます。

💡 皆さんのチームへの提案: 現在社内で使っている Terraform モジュールの開発・運用に、AVM の仕様（一貫インターフェース・テスト手法・セマンティックバージョニング）を参考として取り入れてみてはいかがでしょうか。

3.6.1 AVM はどのように品質を強制しているか — 6 つの仕組み

AVM が他の IaC モジュール提供の取り組みと異なるのは、品質を仕組みとして強制している点です:

#仕組み内容
1公開レジストリへの公開Terraform Registry / Bicep Public Module Registry に公開。透明性と発見可能性を確保
2仕様の策定・公開・維持言語共通仕様 + 言語固有仕様（Bicep / Terraform）を 公式サイト で公開
3貢献ガイドラインの整備各言語向けに、モジュールの開発・公開手順を文書化
4仕様準拠のテスト強制Unit テスト & Integration テストで、モジュールが AVM 仕様に準拠しているかを自動検証
5E2E デプロイテスト各モジュールの Example が実際にデプロイできることを自動テストで検証
6長期サポート保証AVM コアチーム + Microsoft CSS + Azure 製品グループが連携。モジュール所有者の状態に関わらずサポートを継続

3.6.2 AI アシスト IaC 開発（実験的機能）

AVM は GitHub Copilot と連携した AI アシスト IaC ソリューション開発 の実験的サポートを開始しています。AVM Spec Kit を使って、仕様に基づいた Terraform / Bicep コードの生成を加速できます。

4. Terraform の特徴と基本思想

主な特徴

  • マルチクラウド: Azure / AWS / GCP / 3000+ プロバイダ
  • 宣言的 (Declarative): 「望ましい状態」を定義 → 差分だけ適用
  • HCL: JSON より人間に優しい設定言語
  • 状態管理: terraform.tfstate で現在状態を追跡
  • 冪等性（べきとうせい）: 同じコードを何度実行しても、常に同じ結果になる
  • モジュール: 再利用可能なコンポーネント設計

Bicep との比較

観点TerraformBicep
対象マルチクラウドAzure 専用
状態管理明示的 (tfstate)ARM が暗黙管理
AVM 対応✅✅
コミュニティ非常に大きいMicrosoft 中心

本ワークショップでは、皆さんのチームで既に Terraform を標準的にご利用いただいているため、Terraform をベースに進めます。

5. コアワークフロー (init / plan / apply)

terraform init

プロジェクト初期化。プロバイダプラグインのダウンロードとバックエンド初期化を行います。何度実行しても安全。

$ terraform init
Initializing provider plugins...
- Finding hashicorp/azurerm versions matching "~> 4.0"...
- Installing hashicorp/azurerm v4.x.x...
Terraform has been successfully initialized!

terraform plan

変更内容のプレビュー。リソースには一切変更を加えない読み取り専用操作。作成(+) / 変更(~) / 削除(-) の数を表示。

$ terraform plan
Plan: 2 to add, 0 to change, 0 to destroy.

terraform apply

plan の内容を実行しリソースを実際に作成・変更・削除。確認プロンプトあり（-auto-approve でスキップ可）。

$ terraform apply -auto-approve
Apply complete! Resources: 2 added, 0 changed, 0 destroyed.

その他の重要コマンド

コマンド用途安全性
terraform show現在の状態を表示読み取り専用
terraform state list管理リソース一覧読み取り専用
terraform state show <addr>特定リソース詳細読み取り専用
terraform destroy全リソース削除⚠️ 破壊的
terraform console式の対話テスト読み取り専用
terraform fmtコードフォーマットファイル変更
terraform validate構文・型チェック読み取り専用
ベストプラクティス: 常に plan → レビュー → apply の順。CI/CD では plan 結果を PR コメントに投稿し、チームレビューを経てから apply。

6. Demo 01: リソース作成 + lifecycle + 状態ファイル

ディレクトリ: day1/01-resource-creation/

6.1 terraform ブロック & provider

terraform {
  required_version = ">= 1.9"
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"   # 4.x のみ許可
    }
  }
}
provider "azurerm" {
  features {}
  subscription_id = "00000000-..."
}
# マルチリージョン用エイリアス
provider "azurerm" {
  alias = "westus"
  features {}
  subscription_id = "00000000-..."
}

バージョン制約: ~> 4.0 = 4.0.0以上 5.0.0未満（pessimistic constraint）。= 4.1.2 = 完全固定。

Provider エイリアス: マルチリージョンやマルチサブスクリプションデプロイ用。リソース側で provider = azurerm.westus と指定。

6.2 リソース定義と暗黙的依存関係

resource "azurerm_resource_group" "demo" {
  name     = "rg-terraform-demo-day1"
  location = "japaneast"
  tags     = { environment = "demo" }
}

resource "azurerm_storage_account" "demo" {
  name                = "stterraformdemo001"
  resource_group_name = azurerm_resource_group.demo.name   # ← 暗黙的依存関係
  location            = azurerm_resource_group.demo.location
  account_tier        = "Standard"
  account_replication_type = "LRS"
}

azurerm_resource_group.demo.name の参照により、Terraform は RG を先に作成してから Storage Account を作成します。

6.3 lifecycle メタ引数

メタ引数動作ユースケース
prevent_destroydestroy をブロック本番 DB / Key Vault の誤削除防止
ignore_changes指定属性の差分を無視Portal から変更される tags
create_before_destroy新→旧の順で置き換えダウンタイム最小化
replace_triggered_by依存変更時に強制再作成証明書更新時の再デプロイ
lifecycle {
  ignore_changes        = [tags["updated_by"], tags["last_modified"]]
  create_before_destroy = true
}

6.4 状態ファイル (terraform.tfstate)

apply 後にリソース情報が JSON で保存されます。serial（バージョン番号）、lineage（一意ID）、resources（管理対象）が重要フィールドです。

$ terraform state list
azurerm_resource_group.demo
azurerm_storage_account.demo

$ terraform state show azurerm_storage_account.demo
# → id, primary_blob_endpoint, etc. 全属性表示
⚠️ 重要: tfstate には sensitive な値が平文で保存される。本番ではリモート状態（Azure Blob + 暗号化 + ロック）を必ず使用 → Day 2 で詳解。

6.5 デモ実行手順（コピー＆ペースト用）

Step 1: ディレクトリ移動 & 初期化

cd c:\Projects\AVM_Terraform_Workshop\day1\01-resource-creation
terraform init

確認: Terraform has been successfully initialized! と表示。azurerm v4.81.0 がダウンロードされる。

Step 2: Plan（変更プレビュー）

確認: Plan: 2 to add, 0 to change, 0 to destroy. — RG + Storage Account の 2 リソース。

講師ポイント: + 行 = 作成。resource_group_name = (known after apply) = 暗黙的依存関係。

Step 3: Apply（リソース作成）

確認: Apply complete! Resources: 2 added — 約 30 秒。

Step 4: 状態ファイル確認

terraform state list

確認: azurerm_resource_group.demo と azurerm_storage_account.demo の 2 行が表示。

terraform state show azurerm_resource_group.demo

講師ポイント: id（Azure Resource ID）、location = "japaneast"、tags を指しながら「Terraform が追跡する属性」を説明。

Step 5: lifecycle デモ — ignore_changes の動作確認

# 5a. Azure CLI で tags を追加（Portal からの変更をシミュレート）
$rgId = (terraform state show azurerm_resource_group.demo | Select-String "^\s+id\s" | ForEach-Object { $_.ToString().Split("=",2)[1].Trim().Trim('"') })
az tag update --resource-id $rgId --operation merge --tags updated_by=portal_user
# 5b. plan を再実行 → ignore_changes のため差分なし
terraform plan

確認: No changes. Your infrastructure matches the configuration.

講師ポイント: 「Portal で tags を追加したのに差分なし → ignore_changes が効いている。本番で Portal 操作とTerraform を共存させるパターン。」

Step 6: クリーンアップ

terraform destroy -auto-approve

確認: Destroy complete! Resources: 2 destroyed.

7. 変数・ローカル値・出力

7.1 変数の優先順位

優先度ソース例
1 (最高)-var / -var-fileterraform apply -var="env=prod"
2*.auto.tfvarsアルファベット順で自動読み込み
3terraform.tfvarsデフォルト自動読み込み

5defaultvariable ブロック内
6 (最低)対話プロンプトdefault 未設定時

7.2 型システム

基本型: string / number / bool。コレクション: list(T) / map(T) / set(T)。

# object: 構造化データ（optional で省略可能フィールド）
variable "network_config" {
  type = object({
    vnet_cidr  = string
    enable_nsg = bool
    dns        = optional(list(string), [])
  })
}

# tuple: 固定長・異種型
variable "info" { type = tuple([string, number, bool]) }

7.3 sensitive & validation

variable "db_password" {
  type      = string
  sensitive = true   # plan/apply でマスク表示
}
variable "environment" {
  type    = string
  default = "dev"
  validation {
    condition     = contains(["dev","stg","prod"], var.environment)
    error_message = "dev, stg, prod のいずれか"
  }
}
⚠️: sensitive は画面マスクのみ。tfstate には平文保存。

7.4 ローカル値 (locals)

locals {
  name_prefix = "${var.project}-${var.environment}"
  rg_name     = "rg-${local.name_prefix}"
  common_tags = merge({ managed_by = "terraform" }, var.extra_tags)
}

変数と関数を組み合わせて作る中間的な値です。外部からの入力は受け付けません。命名規則の統一やタグの共通化に便利です。

8. Demo 02: AVM Databricks Workspace

ディレクトリ: day1/03-avm-databricks/

モジュール: Azure/avm-res-databricks-workspace/azurerm ｜ GitHub

8.1 コード解説

module "databricks" {
  source  = "Azure/avm-res-databricks-workspace/azurerm"
  version = "~> 0.5"

  name                = "dbw-avm-demo-dev"
  resource_group_name = azurerm_resource_group.demo.name
  location            = azurerm_resource_group.demo.location

  sku = "premium"   # Unity Catalog / RBAC / 監査ログ対応

  # 一貫インターフェース: tags
  tags = local.common_tags

  # 一貫インターフェース: diagnostic_settings
  diagnostic_settings = {
    to_law = {
      name                  = "diag-databricks"
      workspace_resource_id = azurerm_log_analytics_workspace.demo.id
    }
  }
}

8.2 ポイント解説

  • source — Registry 上の AVM モジュールパス。terraform init で自動ダウンロード。
  • version = "~> 0.5" — 0.5.x のみ許可。チーム全員が同じバージョンを使い Breaking Change を防ぐ。
  • sku = "premium" — Unity Catalog / RBAC / 監査ログ対応。データプラットフォームチームなら premium 推奨。
  • tags / diagnostic_settings — 他の AVM モジュール（VNet / Key Vault / Storage）でも全く同じ構文。

8.3 Databricks SKU 比較

SKU特徴推奨シナリオ

8.5 デモ実行手順（コピー＆ペースト用）

Step 1: ディレクトリ移動 & 初期化

cd c:\Projects\AVM_Terraform_Workshop\day1\03-avm-databricks

# サブスクリプション ID を環境変数で渡す（コードに直書きしない）
# TF_VAR_<変数名> は Terraform が自動で読み込む規約です
$env:TF_VAR_subscription_id = (az account show --query id -o tsv)

terraform init

確認: Downloading registry.terraform.io/Azure/avm-res-databricks-workspace/azurerm 0.5.0 for databricks... が表示される。

講師ポイント: 「この瞬間に Terraform Registry から AVM モジュールがダウンロードされている。source + version で指定したバージョンが自動取得される仕組み。」ここで画面を止めて説明。

Step 2: Plan（変更プレビュー）

terraform plan

確認: Resource Group + Log Analytics Workspace + Databricks Workspace の作成が表示される。

講師ポイント: plan 出力で module.databricks 配下のリソースを指し、「AVM モジュール内部ではこれだけのリソースが自動設定されている」と説明。diagnostic_settings が含まれることも確認。

Step 3: Apply（リソース作成 — 約 2-3 分）

terraform apply -auto-approve

確認: Apply complete! — Databricks ワークスペースの作成には 2-3 分かかる。待ち時間中にコードの解説を続ける。

Step 4: ワークスペース URL を確認

terraform output databricks_workspace_url

確認: "https://adb-xxxxxxxxxxxx.x.azuredatabricks.net" 形式の URL が表示される。

Step 5: ブラウザで確認

# PowerShell でブラウザを開く
Start-Process (terraform output -raw databricks_workspace_url)

確認: ブラウザで Databricks UI が開く。「Terraform コードだけでここまでのリソースが作成された」ことを実感してもらう。

Step 6: 作成されたリソースの確認

terraform state list

確認: azurerm_resource_group.demo、azurerm_log_analytics_workspace.demo、module.databricks 配下のリソース群が表示される。

terraform output

確認: databricks_workspace_url、databricks_workspace_id、resource_group_name が全て表示。

Step 7: クリーンアップ

terraform destroy -auto-approve

確認: Destroy complete! — 全リソースが削除される（約 1-2 分）。

💡 講師ヒント: Apply の待ち時間（2-3分）を活用して、「このモジュールは Terraform Registry で公開されている。Registry ページの Inputs / Outputs タブで使えるパラメータが確認できる」と Registry の見方を説明する。
