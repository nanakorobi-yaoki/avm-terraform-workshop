2. モジュール & 依存関係

モジュールとは

Terraform モジュールとは、再利用可能なコードのまとまりです。.tf ファイルが入ったディレクトリが 1 つのモジュールになります。

モジュールソース

ソース構文用途
ローカルsource = "./modules/storage"プロジェクト内
Registrysource = "Azure/avm-res-.../azurerm"AVM 公開モジュール
GitHubsource = "github.com/org/repo//path"プライベート
Azure DevOpssource = "git::https://dev.azure.com/..."社内レジストリ

依存関係

  • 暗黙的依存: 属性を参照することで自動的に順序が決まる — rg = azurerm_resource_group.demo.name
  • 明示的依存: depends_on = [azurerm_resource_group.demo] で明示的に指定
⚠️ よくある落とし穴: depends_on をモジュールに付けると、モジュール内の全リソースが待ちになり、並列度が落ちて apply が遅くなります。また depends_on には変数や式を使えません（静的な参照のみ）。基本は暗黙的依存を使い、本当に順序保証が必要なときだけ depends_on を使ってください。

モジュールの入出力設計

モジュールは関数だと考えると設計しやすくなります。variable = 引数、output = 戻り値、モジュール内部 = 実装詳細（隠蔽）。

原則内容
入力は最小限にoptional() で既定値を持たせ、必須項目を減らす
出力は惜しみなく周辺モジュールが必要とする ID / 名前は必ず output する
Provider を定義しない子モジュールでは provider ブロックを書かない（呼び出し側から渡す）
リソースを作りすぎない1 モジュール = 1 関心事。RG ごと包むのは再利用性を下げる

モジュールの繰り返し — for_each / count

# 複数環境を一括展開（for_each 推奨）
module "storage" {
  for_each = {
    app  = { containers = ["data", "logs"] }
    logs = { containers = ["archive"] }
  }

  source = "./modules/storage"
  name       = "st${each.key}${var.suffix}"
  containers = each.value.containers
}

# 参照は module.storage["app"].id のようにキーでアクセス
⚠️ count ではなく for_each を使う理由: count はインデックス管理のため、リストの途中の要素を削除すると以降のリソースが全て再作成されます（[0],[1],[2] から [1] を消すと [2]→[1] にズレる）。for_each は文字列キー管理なので影響しません。本番環境では致命的な差が出ます。

ラッパーモジュールパターン（SI 事業で最も重要）

AVM をそのまま使うのではなく、自社標準を乗せた薄いラッパーを一層挿すと、案件横断の標準化が一気に進みます。

# modules/corp-vnet/main.tf — 自社標準ラッパー
module "vnet" {
  source  = "Azure/avm-res-network-virtualnetwork/azurerm"
  version = "~> 0.19.0"   # ← version はラッパー内で一元管理（3 桁固定。詳細は 8 章）

  # 命名規則を強制（案件ごとにブレない）
  name = "vnet-${var.customer}-${var.env}-${var.location_short}"

  # 共通タグを強制（課金・監査のため必須）
  tags = merge(var.tags, {
    customer   = var.customer
    env        = var.env
    managed_by = "terraform"
    wrapper_module = "corp-vnet/1.2.0"
  })

  address_space = var.address_space
  subnets       = var.subnets
}
💡 この層の価値: AVM のバージョンアップを1 か所で吸収できます。ラッパーを v1.3.0 に上げるだけで、全案件が同じペースで追従できます。案件リポジトリが直接 AVM を参照していると、バージョン上げが N 件分の作業になります。

バージョン管理と公開

# Git タグでバージョンを固定（ブランチ参照は本番 NG）
module "vnet" {
  # ✗ 悪い例: main が動くと意図せず変更が入る
  # source = "git::https://dev.azure.com/sts/iac/_git/modules//vnet"

  # ✓ 良い例: タグで固定
  source = "git::https://dev.azure.com/sts/iac/_git/modules//vnet?ref=v1.2.0"
}

4. リモート状態管理

ローカル状態の問題

  • チーム共有不可
  • 同時実行で競合
  • sensitive 値が PC 上に平文
  • バックアップなし

Azure Blob Backend

terraform {
  backend "azurerm" {
    resource_group_name  = "rg-terraform-state"
    storage_account_name = "stterraformstate001"
    container_name       = "tfstate"
    key                  = "workshop/demo.tfstate"
  }
}

メリット: Blob Lease でロック（同時実行防止）/ SSE で暗号化 / バージョニングで履歴保持 / RBAC でアクセス制御

ロックはどう動いているか

Terraform は apply 開始時に状態ファイル Blob に対して Blob Lease（排他ロック）を取得します。他の実行が同じ state に触れようとすると即座にエラーになります。

Error: Error acquiring the state lock

Lock Info:
  ID:        3f2a1b4c-...
  Operation: OperationTypeApply
  Who:       runner@fv-az123
  Created:   2026-07-28 09:12:33 UTC
⚠️ force-unlock は最終手段: パイプラインがタイムアウトしてロックが残ることがあります。terraform force-unlock <LOCK_ID> で解除できますが、別の apply が本当に実行中でないことを必ず確認してから実行してください。実行中に解除すると state が壊れます。CI 側では concurrency でそもそも同時実行させないのが正解です（後述）。

知っておくべき state 操作コマンド

コマンド用途危険度
terraform state list管理下のリソース一覧安全
terraform state show <addr>属性の確認安全
terraform state mvリソース名/モジュールのリファクタ時に必須中
terraform state rm管理外にする（実リソースは残る）高
terraform import / import ブロック既存リソースの取り込み中
terraform state pull > backup.tfstate危険な操作前のバックアップ安全
💡 リファクタは moved ブロックで: Terraform 1.1+ では state mv を手で叩く代わりに、コードに moved { from = ... to = ... } を書けます。PR でレビューでき、CI で自動適用され、履歴も残るため、チーム開発では圧倒的に優れています。

state の分割戦略 — どこで切るか

1 つの state が巨大化すると plan が遅くなり、失敗時の影響範囲も広がります。ライフサイクルと変更頻度で切るのが原則です。

tfstate/
  ├─ platform/network.tfstate      # 変更頻度：低、影響：大
  ├─ platform/security.tfstate     # Key Vault, Log Analytics
  ├─ workload/app-prod.tfstate     # 変更頻度：高、影響：小
  └─ workload/app-dev.tfstate

別 state の値を参照するには terraform_remote_state データソースを使います（相手側で output 定義が必要）。

data "terraform_remote_state" "network" {
  backend = "azurerm"
  config = {
    resource_group_name  = "rg-terraform-state"
    storage_account_name = "stterraformstate001"
    container_name       = "tfstate"
    key                  = "platform/network.tfstate"
  }
}

# 参照
subnet_id = data.terraform_remote_state.network.outputs.subnet_ids["app"]

部分バックエンド設定（CI で必須）

backend ブロックには変数が使えません。環境ごとに key を切り替えるには -backend-config を使います。

# backend ブロックは空で宣言
terraform { backend "azurerm" {} }
# CI から環境別の値を注入
terraform init \
  -backend-config="resource_group_name=rg-terraform-state" \
  -backend-config="storage_account_name=${TFSTATE_SA}" \
  -backend-config="container_name=tfstate" \
  -backend-config="key=${CUSTOMER}/${ENV}.tfstate"   # ← 案件×環境で分離
⚠️ state は機密情報です: パスワードや接続文字列は sensitive であっても state 内には平文で保存されます。Storage Account は必ずパブリックアクセス無効 + RBAC 最小権限、可能なら Private Endpoint を適用してください。

6. GitHub Actions × Terraform Deep Dive ★

本日の主題です（33 分）。 AVM が「何をデプロイするか」を標準化するのに対し、GitHub Actions は「それをどう安全に・繰り返し届けるか」を standardize します。両方揃って初めて本番運用に耐えます。

6.1 GitOps の考え方 — Pull Request を「変更申請書」にする

従来の運用GitOps + GitHub Actions
変更申請書（Excel / ワークフローシステム）Pull Request
影響範囲を人が机上で確認terraform plan の自動コメント
上長がメールで承認PR レビュー + Environment 承認ゲート
担当者が手作業で本番投入merge をトリガに自動 apply
作業記録を別途作成Git 履歴 + Actions 実行ログ（改ざん不可）
💡 ISMS / P マーク観点: 「誰が申請し、誰が承認し、いつ何が変わったか」が全て自動で記録されます。監査証跡の作成工数そのものがゼロになるのが、CI/CD 導入の最も大きな副次効果です。

6.2 OIDC 認証 Deep Dive（最重要）

従来方式の何が問題か

  • Service Principal の Client Secret を GitHub Secrets に保存 → 漏洩したら即座にサブスクリプションが危険
  • Secret に有効期限がある → 切れるとパイプラインが突然停止（よくある障害）
  • 定期ローテーションの運用コスト（案件数 × 環境数だけ発生）

OIDC の認証シーケンス

┌──────────────┐                    ┌────────────────┐              ┌───────┐
│GitHub Actions│                    │  Microsoft     │              │ Azure │
│   Runner     │                    │  Entra ID      │              │  API  │
└──────┬───────┘                    └───────┬────────┘              └───┬───┘
       │ ① OIDC トークン要求                 │                           │
       │   (id-token: write が必要)          │                           │
       │                                    │                           │
       │ ② 署名付き JWT を取得               │                           │
       │   claims: sub, iss, aud            │                           │

       │ ③ JWT を提示して Azure トークン要求  │                           │

★ 保存された長期シークレットは一切存在しない

Federated Credential の subject — ここが最頻出のハマりどころ

Entra ID 側に登録する subject が、GitHub が発行する JWT の sub クレームと完全一致しなければ認証は失敗します。トリガの種類ごとに sub の形が変わります。

ワークフローの実行条件登録すべき subject
main ブランチへの pushrepo:ORG/REPO:ref:refs/heads/main
Pull Requestrepo:ORG/REPO:pull_request
environment: production を指定したジョブrepo:ORG/REPO:environment:production
タグ v* の pushrepo:ORG/REPO:ref:refs/tags/v1.0.0
⚠️ 最頻出のエラー: ジョブに environment: を付けた瞬間、sub クレームは ref:refs/heads/main ではなく environment:production に変わります。ブランチ用の Federated Credential しか登録していないと AADSTS700213: No matching federated identity record found で失敗します。承認ゲートを付けるなら environment 用の資格情報を必ず追加してください。1 アプリにつき最大 20 件まで登録できます。

★ 接頭辞も変わる — 「ID 形式の sub」問題

上表の repo:ORG/REPO という接頭辞は、実は常にその形とは限りません。GitHub は組織名・リポジトリ名の改名に耐えるよう、数値 ID を埋め込んだ不変 (immutable) 形式で sub を発行することがあります。

# 古典形式（多くの記事やサンプルはこちら）
repo:contoso-org/avm-workshop:environment:plan

# ID 形式（実際に発行されることがある）
repo:contoso-org@59213077/avm-workshop@1315150240:environment:plan
⚠️ これは実際に本ワークショップの準備中に発生しました。 厤値なのは、設定を確認すると use_immutable_subject は false なのに、接頭辞だけは ID 形式だったことです。つまり「フラグが false だから古典形式のはず」という推測は通用しません。

対処法 — 推測せず、GitHub に聞く。

# 実際に使われる接頭辞を API で取得する
gh api repos/OWNER/REPO/actions/oidc/customization/sub --jq .sub_claim_prefix

本ワークショップの setup-oidc.ps1 / setup-oidc.sh はこの API を叩いて実値を取得し、古典形式と ID 形式の両方を登録します（合計 8 件）。こうしておけば、GitHub 側の仕様がどちらに転んでも動きます。

💡 実務への教訓: OIDC の認証失敗は、ほぼすべて subject の文字列不一致です。デバッグの鉄則は「Actions のログに出ている subject claim をそのままコピーして登録する」こと。azure/login は失敗時に実際の sub をログ出力してくれます。

GitHub Secrets に入れる 3 つの値（いずれも機密ではない）

AZURE_CLIENT_ID       # アプリケーション (クライアント) ID
AZURE_TENANT_ID       # ディレクトリ (テナント) ID
AZURE_SUBSCRIPTION_ID # サブスクリプション ID

# ★ AZURE_CLIENT_SECRET は不要 — これが OIDC の要点
# ワークフロー側での有効化
permissions:
  id-token: write     # ← これが無いと OIDC トークンを取得できない
  contents: read

env:
  ARM_USE_OIDC: true          # AzureRM Provider に OIDC を使わせる
  ARM_CLIENT_ID: ${{ secrets.AZURE_CLIENT_ID }}
  ARM_TENANT_ID: ${{ secrets.AZURE_TENANT_ID }}
  ARM_SUBSCRIPTION_ID: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

権限は最小限に

⚠️ サブスクリプション スコープの Contributor は避けてください。 実運用では ① リソースグループ スコープに限定、② Owner は付けない（RBAC 付与が必要な場合のみ User Access Administrator を別途）、③ 本番と検証で別のアプリ登録を使う、の 3 点を徹底します。OIDC はシークレットを無くしますが、権限過多の問題は解決しません。

6.3 ワークフロー全体設計

PR 作成
  │
  ├─▶ [Job 1] validate  ── fmt / validate / tflint / checkov / conftest
  │        │ 失敗したら以降を実行しない（早期失敗）
  │        ▼
  ├─▶ [Job 2] plan      ── OIDC ログイン → plan -out=tfplan
  │        │              → artifact に保存
  │        │              → PR に結果をコメント（sticky）
  │        ▼
  │     👤 レビュー・承認（branch protection）
  │
merge to main
  │
  └─▶ [Job 3] apply     ── environment: production（承認ゲート）
                          → artifact の tfplan を取得
                          → apply tfplan  ★再 plan しない
なぜ artifact で tfplan を渡すのか: apply 時に再度 plan を実行すると、その間に他の変更が入っていた場合レビューした内容と違うものが適用されます。レビュー済みの plan ファイルをそのまま適用することで、「承認した内容 = 適用された内容」を保証できます。

★ concurrency — state ロック競合を防ぐ

2 つの PR がほぼ同時に merge されると、2 つの apply が同じ state を奪い合い、片方が Error acquiring the state lock で失敗します。ワークフロー側で直列化するのが正解です。

concurrency:
  # state ファイル単位でグループ化（環境ごとに直列実行）
  group: terraform-${{ github.ref }}
  cancel-in-progress: false   # ★ apply 中断は state 破損の原因。必ず false

セマンティックバージョニングと version 固定 ★重要★

AVM モジュールの大半はまだ 1.0 未満です。1.0 未満のモジュールでは、Terraform の ~>（悲観的制約）の挙動が直感と異なるため、事故が起きやすい箇所です。

書き方実際に許容される範囲評価
version = "~> 0.7">= 0.7.0, < 1.0.0 → 0.19 でも 0.99 でも上がる❌ 危険
version = "~> 0.7.0">= 0.7.0, < 0.8.0 → パッチのみ✅ 推奨
version = "= 0.19.0"完全固定✅ 本番・顧客納品
version = "~> 4.2"1.0 以上なら >= 4.2, < 5.0 でマイナーまで許容✅ provider 向け
⚠️ 実際にこの資料の作成中に踏んだ罠: 本ワークショップのデモコードは当初 version = "~> 0.7" と書いていました。「0.7 系に固定した」つもりでしたが、~> を2 桁で書くと < 1.0 の意味になるため、terraform init が最新の 0.19.0 を取得しました。0.8 以降で resource_group_name が parent_id に置き換わっていたため、init の時点で Error: Unsupported argument となりデモが動きませんでした。

教訓: 1.0 未満のモジュールは ~> 0.19.0 のように3 桁で書く。顧客納品物では = 0.19.0 の完全固定を推奨します。
# 1.0 未満の AVM モジュール（＝ほとんど）
version = "~> 0.19.0"   # ✅ 0.19.x のみ（パッチ許容）
version = "= 0.19.0"    # ✅ 完全固定（顧客納品）
version = "~> 0.19"     # ❌ 0.99 まで上がる = 破壊的変更を拾う

# provider（1.0 以上）
version = "~> 4.2"      # ✅ 4.x のマイナー更新は許容
💡 さらに強い保証: .terraform.lock.hcl
provider の正確なバージョンとハッシュを記録するロックファイルです。必ず Git にコミットしてください（.gitignore に入れてはいけません）。CI では terraform init -lockfile=readonly を使うと、ロックファイルに無い provider が入ってきた時点で失敗させられます。
※ ロックファイルは provider のみで、モジュールのバージョンは記録されません。モジュールは version 制約で固定するしかない点に注意してください。

破壊的変更への備え（顧客納品を前提に）

  1. バージョンを上げるのは意図的な作業 — terraform init -upgrade は「更新したいとき」だけ実行する
  2. 更新は必ず PR 経由 — Dependabot / Renovate でバージョン更新 PR を自動生成し、CI の plan で差分を確認してからマージ
  3. CHANGELOG を読む — AVM は GitHub リポジトリでリリースノートを公開。BREAKING CHANGE の記載を確認
  4. ラッパーモジュールで吸収 — 自社ラッパー層で AVM を包んでおけば、AVM 側の引数名変更をラッパー内 1 箇所の修正で全案件に反映できる

💡 したがって論点は「Excel をやめるか」ではありません。 本当の論点は 「その納品物が、実際に適用された構成と一致していることを、どうやって証明するか」です。信頼性はファイル形式ではなく生成と検証の仕組みから生まれます。以下ではまず評価軸を決め、その上で選択肢を比較します。

10.2 「信頼できる」を 6 つの評価軸に分解する

「信頼できる方法」を漠然と探すと比較ができません。まず何を満たせば信頼できるのかを定義します。

#評価軸満たせていないと起きること
1機械検証（型・必須・値域）10.0.0.0/6 のような誤値が apply まで発見されない
2差分レビュー（Git で diff できる）変更点が目視確認となり、レビューが形骸化する
3自動生成（人手を介さない）転記ミス。コードと納品物が徐々に乖離する
4トレーサビリティ（どのコードから生成されたか）「この Excel はいつ時点のものか」が誰にも答えられない
5改ざん検知（手編集を検出できる）納品後に誰かが Excel を直接編集し、実環境と食い違う
6非エンジニア可読性エンドユーザー様の情シス／監査部門が読めない
ポイント: Excel は 6（可読性）に非常に強く、2（差分）に非常に弱い形式です。一方 YAML/Markdown は 2 に強く 6 に弱い。どちらか一方を選ぶ必要はありません — 正をコードに置き、そこから複数形式を生成すれば、両方の長所を取れます。

10.4 入力側を固める — 生成元の品質がそのまま納品物の品質になる

納品 Excel を自動生成している以上、その信頼性は「生成元のパラメータがどれだけ検証されているか」で上限が決まります。検証されていない値から生成された美しい Excel は、誤値を美しく印刷しているだけです。

Step 1: そもそも「埋める項目」を減らす（最も効果が大きい）

AVM のセキュア既定値をそのまま活かし、optional() でデフォルトを持たせます。パラメータ 200 項目 → 10 項目にできれば、Excel かどうかは大きな問題ではなくなります。

variable "workload" {
  description = "エンドユーザー様に入力いただく項目はこれだけ"
  type = object({
    name        = string                              # 必須
    environment = string                              # 必須
    location    = optional(string, "japaneast")      # 以下は既定値あり
    sku         = optional(string, "Standard")
    enable_private_endpoint = optional(bool, true)  # WAF 既定値
    retention_days          = optional(number, 90)
  })

  validation {
    condition     = contains(["dev", "stg", "prod"], var.workload.environment)
    error_message = "environment は dev / stg / prod のいずれかを指定してください。"
  }
  validation {
    condition     = can(regex("^[a-z0-9]{3,20}$", var.workload.name))
    error_message = "name は英小文字と数字のみ、3〜20 文字で指定してください。"
  }
}
Excel の「入力規則」に相当する機能が Terraform 側にあります。 validation ブロック（条件 + 日本語エラーメッセージ）、type による型強制、sensitive = true、リソース側の lifecycle { precondition }。これらは plan の時点で検証されるため、本番適用前に必ず止まります。

10.5 ★本命★ 納品物を「検証可能」にする 3 つの仕掛け

ここが今回のご質問に対する中心的な回答です。形式を変えずに、評価軸 ①④⑤（機械検証・トレーサビリティ・改ざん検知）を埋めます。

仕掛け ①：納品物に「刻印」する（トレーサビリティ）

生成した Excel の先頭に「メタ情報」シートを必ず 1 枚追加します。これだけで「この Excel はいつ・どのコードから生成されたのか」に即答できるようになります。

項目値の例なぜ必要か

Git コミットハッシュ7a3f2d3納品物 → コードの逆引き
リリースタグv1.2.0契約・請求単位との紐付け
Terraform バージョン1.15.8再現性の担保

💡 ISMS / P マーク観点: この 1 シートが、監査時の「この設定書はどのように作成され、正しさをどう担保していますか？」という問いへの回答そのものになります。口頭説明ではなく成果物自体が証跡になる点が重要です。

仕掛け ②：CI で「再生成して差分ゼロ」を検証する（改ざん検知）

納品物が手編集されていないことを機械的に証明します。CI でもう一度生成し、コミット済みのものと一致するか検証します。

⚠️ 技術的な注意 — .xlsx をバイト比較してはいけません。 xlsx は ZIP 圧縮されたバイナリで、内部に生成日時のタイムスタンプを含みます。同じ内容でも生成のたびにバイト列が変わるため、単純な diff や git diff --exit-code は必ず失敗します。正規化したテキスト中間表現を経由してください。
# 生成物は「正規化 JSON」と「xlsx」の 2 つ。Git に置くのは正規化 JSON。
# xlsx は正規化 JSON から決定的に生成される派生物という位置づけにする。

- name: "パラメータシートを再生成"
  run: |
    python tools/gen_param_sheet.py \
      --params params/contoso-prod.yaml \
      --schema schema/params.schema.json \
      --format json \
      --output dist/contoso-prod.normalized.json

- name: "手編集されていないことを検証"
  run: |
    # 差分があれば = 誰かが成果物を直接編集した = ビルド失敗
    git diff --exit-code dist/contoso-prod.normalized.json \
      || { echo "::error::納品物が手編集されています。パラメータ側を修正してください"; exit 1; }

仕掛け ③：「適用実績」を併せて納品する（実態との一致証明）

パラメータシートは「こう設定するつもり」の文書です。これに対し terraform show -json は「実際にこうなっている」という実態です。両者を突き合わせて初めて「一致している」と言えます。

terraform show -json tfplan > dist/plan.json          # 適用予定
terraform show -json > dist/state.json                # 適用実績（apply 後）

# 納品セットに同梱し、SHA-256 を納品書に記載
sha256sum dist/*.json dist/*.xlsx > dist/SHA256SUMS.txt
まとめ: ①②③ を入れると、納品物は「Excel ファイル」から 「コミットハッシュに紐づく、再生成可能で改ざん検知付きの成果物」に変わります。エンドユーザー様に渡す見た目は今までと全く同じまま、信頼性だけが上がります。既存の契約様式・承認フローを変更する必要がありません。

10.8 逆方向 — エンドユーザー様から Excel で提出される場合

納品は Excel 出力でも、要件ヒアリング時にはエンドユーザー様から Excel で値をいただくケースは残ります。この向き（Excel → コード）だけは転記ミスのリスクがあるため、一方通行の自動変換を CI に載せます:

  1. Excel は受付フォームと割り切り、リポジトリにコミット
  2. CI で xlsx → YAML に自動変換（openpyxl / pandas）— 手転記を廃止
  3. 変換後の YAML を JSON Schema で検証 → 失敗したら PR をブロック
  4. YAML を Git にコミット → 差分がレビュー可能に
  5. 生成された .tfvars / YAML の手編集は禁止（CI でチェック）
⚠️ 必ず守るルール: 変換は必ず一方向にしてください。Excel とコードの双方向編集を許すと、どちらが正か分からなくなり、現状より状況が悪化します。

- name: 納品物が手編集されていないことを検証
  run: |
    # xlsx は生成日時を含む ZIP バイナリなのでバイト比較できない。
    # 決定的な正規化 JSON を再生成し、コミット済みのものと比較する。
    python tools/gen_param_sheet.py \
      --params params/contoso-prod.yaml \
      --schema schema/params.schema.json \
      --format json \
      --output dist/params.normalized.json
    git diff --exit-code dist/params.normalized.json \
      || { echo "::error::納品物が直接編集されています。params/ 側を修正して再生成してください"; exit 1; }
成果: main にマージされた瞬間、納品用パラメータシートが Actions のアーティファクトとして生成されます。「デプロイした内容」と「納品したドキュメント」が原理的に一致し、乖離が発生しません。
